# งานที่ 3: ระบบไอเทมและการก่อกวน

เอกสารสำหรับผู้พัฒนาคนที่ 3: เพิ่มไอเทมสุ่มเกิดและกลไกโจมตี/ป้องกัน/สะท้อนกลับใน FFA และทีม 2v2 โดย server เป็นผู้ตัดสินผล

## เป้าหมาย

- เพิ่มไอเทมที่เกิดแบบสุ่มในระหว่างการแข่งขัน โดยเวลา/ตำแหน่งไม่ตายตัว
- เพิ่มการโจมตีที่จำกัดผลกระทบ มีวิธีป้องกัน และตรวจสอบได้จาก server
- รองรับเป้าหมายรายคนใน FFA และเป้าหมายเป็นทีมใน 2v2
- รองรับจุดปฏิสัมพันธ์ในฉาก เช่น เดินไปดึงสวิตช์/ชักปักไฟฝั่งตรงข้าม ตามที่ UI และ scene รองรับ

## บริบทและการประสานงาน

- ห้องและ Socket.IO อยู่ที่ `server/game/rooms.js`; engine อยู่ที่ `server/game/engine.js`
- ไคลเอนต์ใช้ `public/js/`; ตรวจ input และ scene movement ที่มีอยู่ก่อนเพิ่ม interaction
- งานที่ 1 เป็นเจ้าของ game mode, player/team identity, phase และ state scope
- งานที่ 2 เป็นเจ้าของ progress broadcast; แจ้งงานที่ 2 เมื่อ item effect เปลี่ยนสถานะที่ควรแสดง
- ตกลง schema item, event และ API ร่วมกัน หลีกเลี่ยงแก้ไฟล์ห้อง/engine เดียวกันโดยไม่ประสาน

## ไอเทมขั้นต่ำ

1. **Config Erase (โจมตี):** รีเซ็ตค่าที่คู่แข่งตั้งไว้หนึ่งรายการกลับค่าเริ่มต้น/ค่าผิด ห้ามรีเซ็ตทั้งด่านในครั้งเดียว
2. **Config Glitch (โจมตี):** ทำให้การตั้งค่าหนึ่งรายการเพี้ยนแบบจำกัดและชั่วคราว มีสัญญาณเตือนและทางแก้
3. **Shield (ป้องกัน):** บล็อกการโจมตีหนึ่งครั้งหรือคุ้มกันในช่วงเวลาที่กำหนด
4. **Reflect (สะท้อนกลับ):** สะท้อนการโจมตีหนึ่งครั้งกลับผู้โจมตี ต้องป้องกันการสะท้อนวนซ้ำ
5. **Switch/Lever (ปฏิสัมพันธ์ฉาก):** ผู้เล่นเดินไปยังจุดที่กำหนดแล้วกดใช้ เพื่อเปิดผลรบกวนชั่วคราวหรือสลับ/ดึงสวิตช์ฝั่งตรงข้าม หากเพิ่มกลไกนี้ การเคลื่อนที่/ระยะถึงจุดต้องตรวจที่ server

## Spawn, inventory และสมดุล

- Server สุ่มเวลาและจุดเกิดจากชุดตำแหน่งที่อนุญาต; client แสดงตำแหน่งและขอเก็บเท่านั้น
- กำหนดอัตรา/ช่วงสุ่ม, อายุไอเทมบนฉาก, inventory cap, cooldown, ระยะเวลา effect และจำนวนผลต่อรอบใน server config
- ออกแบบการเกิดให้ไม่เอื้อผู้เล่น/ทีมใดตั้งแต่เริ่ม เช่น ใช้ตำแหน่งที่เข้าถึงได้เท่าเทียมและสุ่มซ้ำตามกติกา
- ป้องกันการเก็บซ้ำ, ใช้ไอเทมซ้ำ, เก็บไอเทมที่หมดอายุ และส่งคำขอจากผู้ที่อยู่นอกการแข่งขัน
- เอฟเฟกต์มีขอบเขตและเวลาสิ้นสุดชัดเจน พร้อมวิธีแก้คืนหรือตอบโต้

## Target rules

- FFA: การโจมตีเลือกคู่แข่งที่ยังไม่จบเกม ห้ามเลือกตัวเอง
- 2v2: การโจมตีเลือกได้เฉพาะทีมคู่แข่ง ห้ามโจมตีเพื่อนร่วมทีม
- ผู้เล่น/ทีมที่จบแล้วไม่สามารถถูกโจมตีเพิ่ม
- Shield และ Reflect ทำงานตามลำดับที่กำหนดและส่งผลได้ครั้งเดียวต่อ charge; Reflect ต้องไม่เด้งกลับไปมา
- เมื่อไม่มีเป้าหมายที่ถูกต้อง ให้ปฏิเสธคำขอพร้อมเหตุผลและไม่ใช้ไอเทม

## ความปลอดภัยและ Network

- Client ขอเก็บ/ใช้/เลือกเป้าหมาย/ใช้งานสวิตช์ได้ แต่ server เป็นผู้ตรวจและเปลี่ยนสถานะทั้งหมด
- ตรวจ room membership, phase, inventory, cooldown, target eligibility, distance (ถ้ามี), item expiration และ request ID เพื่อกัน replay
- Client ห้ามกำหนด item type, drop time, effect, attacker ID, target ID ที่เชื่อถือได้ หรือผลสำเร็จเอง
- สุ่ม spawn และจัดเก็บสถานะ active effect ฝั่ง server เท่านั้น
- แจ้ง event ที่จำเป็น: spawn, pickup result, item use result, blocked, reflected, effect start/end, switch activation และ error
- Broadcast เฉพาะข้อมูลที่ผู้เล่นควรเห็น; ไม่ส่งค่าลับของโจทย์หรือรายละเอียดการตั้งค่าของคู่แข่ง
- งานที่ 2 ควรได้รับสถานะทั่วไป เช่น ผู้เล่น/ทีมกำลังถูกรบกวน เพื่อแสดงใน progress HUD โดยไม่เปิดข้อมูลคำตอบ

## UI

- Inventory แสดงไอเทม จำนวนคงเหลือ และผลโดยย่อ
- ก่อนใช้ไอเทมโจมตีให้เลือกเป้าหมายที่ถูกกติกาและยืนยันการใช้
- แจ้งผลเมื่อโจมตีสำเร็จ ถูก Shield บล็อก ถูก Reflect กลับ หรือใช้ไม่ได้ พร้อม feedback ที่ชัดเจน
- ไอเทมในฉากแสดงตำแหน่งและเวลาหมดอายุอย่างเหมาะสม; interaction point ต้องมองเห็นและเข้าใจวิธีใช้
- เอฟเฟกต์ไม่บังเทอร์มินัลหรือข้อมูล progress และรองรับจอเล็ก

## เกณฑ์ยอมรับ

- spawn เกิดจาก server ด้วยเวลาไม่ตายตัวและตำแหน่งที่อนุญาต
- pickup/use ปลอม, ซ้ำ, หมดอายุ, cooldown ไม่ผ่าน หรือ target ผิดถูกปฏิเสธโดยไม่เปลี่ยน state
- Config Erase และ Config Glitch มีผลจำกัด ระบุผู้ถูกกระทบได้ และสามารถเล่นแก้โจทย์ต่อได้
- Shield บล็อกและ Reflect สะท้อนตามกติกาโดยไม่เกิด loop
- FFA และ 2v2 บังคับ target rules ถูกต้อง และห้ามรบกวนผู้เล่นที่จบแล้ว
- reconnect ไม่ทำให้ inventory, spawn หรือ effect ถูกสร้างซ้ำ และได้รับสถานะปัจจุบันจาก server
- (ถ้าทำ Switch/Lever) server ยืนยันตำแหน่ง/ระยะและป้องกันการ activate ซ้ำ
- มี UI feedback และ error สำหรับทุกผลหลักของการใช้ไอเทม

## ขั้นตอนสำหรับผู้พัฒนา

1. ตรวจ state และ command handlers ปัจจุบัน รวมถึงกลไก movement/interact
2. ประสาน data model/event กับผู้ทำงานโหมดและ progress
3. ทำ item lifecycle/effect ฝั่ง server ก่อน แล้วเชื่อม client UI
4. เพิ่ม/ปรับ automated tests สำหรับ spawn, pickup, target validation, shield, reflect, expiration, reconnect và regression
5. สรุปค่าความสมดุลที่เลือกและอัปเดตเอกสาร
